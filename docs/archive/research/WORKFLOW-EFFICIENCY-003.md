# WORKFLOW-EFFICIENCY-003｜降低 Agent 工作流的重複成本

研究日期：2026-09-25。產品主責；一名工程子 Agent 獨立唯讀分析程式邊界。範圍是研究及建議，本文件不是新增的必讀規範；未修改遊戲、協作規則、測試或 Git 設定。

## 判斷

優先順序：**縮小任務上下文 → 落實既有驗收證據沿用 → 按責任拆程式 → 按獨立性派 Agent**。暫不增加角色數量。改善目標是完成同等品質工作所需的總成本，同時觀察耗時與 token，不能把更多平行工作帶來的較短等待誤當成較少 token。

這是根據本機結構與公開工程經驗提出的優先級，尚未做前後對照實驗。檔案 bytes、行數及工具輸出字元都不等於實際計費 token；磁碟上存在的檔案也不會因此自動全部載入。

## 建議的日常流程

1. **產品建立精簡任務資料**：成果、唯一寫入者、允許檔案／區段、不可改規則、相關入口、基線、必要驗收、未決依賴。工單保存完整現況，工作板只存狀態與連結，避免三份文件各抄一次結論。
2. **實作者按索引讀取**：先讀介面及本次相關函式，再沿依賴擴展。一般搜尋排除備份、生成測試結果及原畫目錄；任務涉及它們時明確加入。保留一份原始資料，不能因省 token 刪除證據。
3. **先做短檢查再跑必要套件**：先確認載入、測試定位器及一次主要操作。測試失敗分類為產品、測試程式或環境問題，避免直接重跑全部長流程。
4. **凍結後交工程師**：交付真實 diff、已確認風險及可驗證證據。工程師獨立審查，按風險實測；相關依賴未變的測試不機械式再跑。補正後查新差異、原故障及受影響回歸。
5. **產品一次整合驗收**：指定一人更新資源版本；報告區分本次實跑、沿用證據與未驗證項目。狀態未變時不反覆抄錄或輪詢。

工具預設回傳成功／失敗、影響檔案、關鍵錯誤及完整產物位置；成功時不印整份 JSON、DOM 或 diff。失敗時保留退出碼和可重現線索，再按需展開，不能用截短輸出掩蓋錯誤。

### Agent 數量

通常由產品協調一名主責，凍結後喚起工程師；小型文件整理由產品完成。獨立研究、素材製作或已固定介面的不同模組可平行。會寫同一檔案、需等待前一步結果，或每人都必須理解全系統的任務，先排好順序。

跨角色交接只提供本次必要背景及可追溯連結；不要慣例複製整段對話。保留五種專長，不等於每次同時啟動五個程序。新增「省 token Agent」會帶來新的交接，現階段沒有必要。

## 程式拆分候選

下表是後續工單候選，尚未實作。先明確界面與狀態擁有者，再搬程式；只搬到新檔卻繼續存取原本所有共享變數，通常無法縮小閱讀範圍。

| 優先 | 邊界及來源 | 預期用途 | 必須保持的行為 |
| --- | --- | --- | --- |
| 1 | `story-campaign.js:66–153` 舞台圖片載入／預載／繪製，約 6,503 bytes | 美術任務集中閱讀舞台模組和 `story-stage-assets.js` | 當前節點與進度改成明確輸入；取消、圖片請求代號、fallback、互動前的預載邊界不變 |
| 2 | `game.js:38–110,734–784,1540–1653` 音效服務與設定，約 11,516 bytes | 音效問題可避開傷害、回合及大量畫面碼 | 保留 `window.playSfx` 等相容入口、inline handler、載入順序、存檔鍵、使用者手勢解鎖與音樂清理；拆分本身不等於修復無聲問題 |
| 3 | `story-campaign-data.js` 按章群整理故事、證據及閱讀分組 | 劇情任務只讀本章與共享資料 | builder 的 step ID、節點順序、V1/V2 語意、全域註冊及腳本載入相容 |

資料檔拆分收益取決於未來是否常做單章修改，可晚於前兩項。`story-stage-assets.js`（8,088 bytes）及測試 helper（4,511 bytes）已小且職責相對清楚，先維持。既有 energy engine 透過少量 API 輸出結果，UI 消費事件／frames，是較好的範例。

過長函式行應在被修改的模組內改善可讀性，讓搜尋和 diff 有用；不做全專案格式重排。空白格式調整可能增加整檔 token，因此衡量的是完成局部任務所需讀取量，不是越少行越省。

## 實施順序與驗收

| 階段 | 建議產物 | 完成判準 |
| --- | --- | --- |
| A：先整理資訊入口 | 精簡角色入口、歷史檔連結、當前任務索引、程式與測試地圖 | 抽取近期不同類型需求，能定位必要檔案；使用者限制、未決事項及舊證據仍可追溯 |
| B：將既有流程工具化 | 小型測試對照清單、摘要輸出、來源與證據指紋 | 已知變更選到正確測試；未知依賴保守擴大；失敗不記成通過；全文可按路徑查閱 |
| C：建立可靠版本基線 | 目前任務凍結後評估本機 Git、忽略生成物及大型原稿的策略 | 現有檔案完整保存、工作樹可辨認；不自動推到遠端。仍保留共享檔單一寫入者 |
| D：逐項拆邊界 | 每次一張有基線與明確介面的拆分工單 | 必要規則／存檔／入口相容測試、相關互動驗收及獨立工程審查通過 |

B 階段的證據指紋須包含相關來源及遞迴依賴、測試程式／輸入、測試環境／設定及所需素材。CSS、window globals、HTML 載入與共用 helper 也算依賴，不能只看被改檔案。先做可解釋的選測及證據驗證，再考慮自動略過測試；對未知影響採保守回歸。

挑五個相近難度的後續任務試行，記錄：首次有效修改與總完成時間、同版本檔案重讀量、工具輸出量、交接次數、無變更卻重跑的套件，以及退回補正／逃逸缺陷。若能取得可靠任務用量，再比較輸入、輸出和快取 token；否則字元量只當代理指標，不換算節省百分比。少量試行用來找方向，不足以證明普遍因果。
