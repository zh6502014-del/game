## 八項設計洞見與本專案接點

### 1. 抓點先保持準確，重量放在姿態與陰影

**Nightfall 提案。** 指標平移直接控制抓點；角度、抬升與放手後回位才加入阻尼。若先對整張牌的位置做追隨彈簧，快速拖曳時卡片會落後，合法目標也可能和使用者看見的位置分離。S4 支持時間步長一致的平滑方法，但沒有主張所有輸入都應平滑。

自由決鬥的 `game.js` 已儲存 `offsetX/offsetY` 並直接更新 body 層 ghost。其抓點是從旋轉後的 bounding box 比例換算，不能準確代表旋轉卡片的本地位置。應先建立包含布局、祖先變換與 `transform-origin` 的 local→viewport 映射 `M`，以 `g = M⁻¹(pointerDown)` 取得本地抓點；把 ghost 的旋轉原點改成抓點，不會修正先前算錯的 `g`，兩者不是替代方案。

對已換算至同一座標系的 2D 仿射變換，可寫成 `p = L + o + A(g − o) + t`，因此定位須解 `L = p − o − A(g − o) − t`。`p` 為目前指標、`L` 為布局定位、`o` 為變換原點、`A` 為縮放／旋轉等線性部分、`t` 為額外平移；只有 `o = g` 且 `t = 0` 才能簡化為 `topLeft = pointer − localGrab`。若定位容器本身有變換，還須把解出的定位轉回其 CSS 座標系。

目前 `card-surface.css` 的 ghost 有 `translateY(-14px) scale(1.04)`；若保留，必須將有效平移 `t` 納入補償，或把抬升感移到不影響抓點的陰影／裝飾層。3D 透視不能直接套用上述 2D 逆矩陣：第一版原型可先限制拖曳為 2D；要保留透視則需依卡片平面做逆投影，再驗證投影抓點。

故事模式目前是「角色／技能來源＋指向箭頭」，不是整張牌跟著手移動；保留這個清楚契約，不因自由決鬥有實體拖牌就硬套同一手勢。可共享目標提示與取消規範，不必共享相同位移模型。

**升級驗收**：九宮格抓點、左右扇形牌、快速折返與 30／60／120 Hz 採樣；每次已處理的 pointermove 後，投影抓點與該事件座標誤差不超過 2 CSS px。另記錄真實事件到 paint 延遲，不能把 DOM 座標準確當成實機低延遲證明。

### 2. 實體感首先來自同一張完整卡片

**Nightfall 提案。** 手牌、拖曳、放置、翻面使用同一組原畫、卡名列與框，動畫只改姿態。不可用壓扁卡身、褪成透明或重新套一個不同外觀的「預覽殼」代替拿起同一張牌。

現有 DRAG-UI-005 已處理拖曳卡面樣式漏接；`PHYSICAL-MOTION.md` 與 `character-art.css` 已建立不透明正反面、各偏移 0.7px 的雙面及 1.4px 側緣。保留其 280／680／340ms 翻牌節奏，這些全是 Nightfall 現況，不是爐石參數。檢查 90° 附近的實際可見面，比只檢查 opacity 更有意義。

**需後續評估**：故事 `playEvent()` 的閃避目前把角色整體 opacity 降到 `.4`。若「角色卡也是實物」是產品契約，可改以獨立月紫殘影表達速度，卡身／數值仍不透明；這是靜態程式發現及候選調整，本單未改也未重現其完整視覺。

**升級驗收**：沿用 `tests/flip-material.cjs` 的近側緣採樣，再加入拖曳→放置→翻面連續材質比對、素材載入失敗及取消中途檢查。不要用整張卡父層 filter／opacity／裁切破壞 `preserve-3d`。

### 3. 高度、接觸與陰影要說同一件事

**Nightfall 提案。** 提起時柔化並偏移接觸陰影；落地時先縮回接觸陰影，再衰減餘震。陰影應在卡面外的獨立層，不能用父層濾鏡把翻牌立體結構壓平。卡片厚度保持一致，不隨「重量」縮放厚薄。

初始調整範圍：小手牌抬升 6–10 CSS px、桌面放置牌 10–14px；角度上限約 ±5°；陰影模糊由約 6px 增到 14px，透明度同時降低。這只是待 A/B 的本地視覺尺度，沒有真實公尺／公斤含義，不能套在所有尺寸後就宣稱物理真實。

**取捨與驗收**：抬得太高會蓋住目標，過深黑影會混入墨綠場景。桌面與窄螢幕各取靜止、抓起、拖曳、落定四幀，檢查方向一致、無穿桌、數值完整；背景日夜變化下仍能辨別牌與桌面。

### 4. 放手回位可有重量，不能像橡膠反覆彈跳

**Nightfall 自訂模型候選。** 對姿態或未提交拖曳回位，以質量正規化的二階系統表達：

`q″ + 2ζω q′ + ω²(q − goal) = 0`

其中平移的 `q` 用 CSS px、角度用 rad、時間用秒、`ω` 用 rad/s、`ζ` 無單位。初始候選為 `ζ=1`、`ω=24 rad/s` 的臨界阻尼；使用解析更新或經測試的時間步長模型，不用每幀固定比例 lerp。臨界阻尼不保證任意初速都不越過目標，仍需初速限制與桌面非穿透約束，避免快速甩牌後長距離飛走或穿桌。這個方程與參數選擇是一般模型在本遊戲的提案，絕不是原作係數。[S4](https://theorangeduck.com/page/spring-roll-call)

合法出牌由操作在放手時提交一次，後面的落定動畫只呈現既定位置；非法放置回到手牌，不能回位途中又觸發出牌。已有時長足夠時先在其區間內調曲線，不加長規則等待。

**升級驗收**：同一初始條件在不同 timestep 的回位曲線誤差門檻先設 1 CSS px／0.2°；終點速度與位置皆收斂，無穿桌、無無限尾巴、無額外 RNG。模型測試通過後仍需實機幀率觀察。

### 5. 攻擊形狀會教玩家規則，不能只按酷炫程度挑效果

**公開證據**：S2 的棋盤動畫改動，是為了讓玩家不再誤以為會反傷；不是「所有卡牌攻擊都該發子彈」的建議。[開發者原文](https://hearthstone.blizzard.com/en-us/news/20271423)

**本專案接點**：FX-JOBS-006 已分成劍客斬擊、刺客雙刃掠影、坦克短距盾擊、槍手曳光。繼續用「預備→出手→接觸→回復」講明來源、方向與結果；坦克盾型停在接觸區短推，避免被讀成投擲盾牌。反擊用真正發動者職業，領域／灼傷不偽裝普通碰撞。

**升級驗收**：在既有職業 × 雙向 × 命中／閃避／護盾矩陣上，加無色版本或短時盲辨試看，確認差異來自輪廓和動作。故事模式已有職業前進距離與槍手支線，但命中斬痕仍較共用；若產品要統一兩模式，應交接「語意 profile」而不是直接共用依賴 `.slot` 的整個 DOM 特效模組。

### 6. 接觸是音畫數值的共同事件，回復不能搶在命中前

S3 明確以施放／命中等節拍設計聲音，而不是只追求更多音效。[聲音團隊訪談](https://hearthstone.blizzard.com/en-us/news/23964694)

**Nightfall 提案**：使用唯讀 `actionId + eventIndex` 的呈現識別，將來源姿態、命中特效、顯示 HP／盾、浮字與相應聲音錨在同一個接觸事件。最終引擎狀態仍一次結算；逐幀數值是顯示快照，不能為動畫重算傷害。

| 呈現階段 | 畫面與聲音契約 | 邊界 |
| --- | --- | --- |
| commit／預備 | 已合法提交；來源亮起／短蓄力；可播拿牌或施放聲 | 不提前播受傷聲、不提前顯示傷害 |
| advance／出手 | 近戰前壓或槍手射擊；守方閃避可先動 | 路線只展示既定結果，不能碰撞後再判定 |
| contact／接觸 | 同一事件更新顯示數值、命中／盾痕、浮字、hit／shield 聲 | miss 只有閃避資訊；無命中火花；全盾吸收無生命受傷回饋 |
| recover／回復 | 攻擊方回原位，接觸餘光衰減，結果保留可讀 | 不在回位後才補命中；不因餘光阻塞下一個已排程事件 |

現況：自由決鬥保留 `80 + index×540ms` 與 110–210ms 接觸等待，但 `game.js` 的 `damageDirect()` 等仍可在結算時先呼叫聲音；應先盤點並去除重複來源，再考慮接觸統一。故事模式已使用 `frames`、逐事件計數更新／聲音、接觸後回位，且已有獨立複審，不能再列成「尚無順序播放」。

**升級驗收**：以單一性能時鐘記錄 `advance/contact/counter-update/audio-request/recover`；先要求接觸與顯示更新同一 callback，音效請求偏差不超過一個 60Hz 畫格。實際出聲另受解碼／設備延遲影響，需錄音或 loopback 證據；API 呼叫時間不等於聽覺同步。也測靜音、拒播及缺音源，確保不重播、不阻塞。

### 7. 精緻的環境應把注意力交給正在作用的牌

S5 提供另一款卡牌遊戲的設計者範例：卡牌是主角，局部方向性光線可以攜帶局勢資訊。[MARVEL SNAP 原設計者說明](https://www.tiffanysmart.com/work/marvel-snap)

**Nightfall 推論**：攻擊源、合法目標、盾面各有短促局部光，場地紋章降低對比；同時只突出正在結算的來源與目標。不複製 SNAP 的玻璃／霓虹；採本專案古金和墨綠，也不在中央重新加入使用者已要求移除的日夜文字。

**取捨與驗收**：重擊不等於全桌爆亮，聲音也不能每一粒碎光都觸發。用同一段多事件戰鬥檢查「可否一眼指出誰攻擊誰、盾或生命發生什麼」，並確認浮字、卡名和操作不被場景層覆蓋；不以粒子數或畫面亮度當品質指標。

### 8. 取消與減少動態是同一體驗的必要分支

S6 說明使用者應能停用非必要的互動動態；Nightfall 的直接操控仍需可用，資訊不能跟著裝飾一起消失。[W3C 解說](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions)

**既有能力**：自由決鬥 `NDCombatFX.cancel()` 已清 timer／動畫／圖層並結束等待；故事模式有 `playToken`、frames、輸入鎖、旋轉與減少動態途中切換。承接已完成的 `STORY-BATTLE-UI-001`，升級測試「取消在每一個事件邊界」：提交前取消不消耗行動；提交後取消只結束呈現並對齊已結算快照，不能撤銷規則或再次扣資源。

減少動態保留直接拖曳／靜態指向、合法目標、卡正面、HP／盾數字、事件文字與日夜狀態；關閉旋轉掃光、慣性尾巴、相機晃動與粒子。音量／靜音仍獨立。途中切換需清掉既有 WAAPI 與聲音排程，再正確顯示當前結果，不能只縮短 CSS duration。
